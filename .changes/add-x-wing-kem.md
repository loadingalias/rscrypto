Add the X-Wing hybrid KEM of ML-KEM-768 and X25519 from draft-connolly-cfrg-xwing-kem-11, behind the new `x-wing` leaf feature, part of `key-exchange`. draft-irtf-cfrg-concrete-hybrid-kems-04 names the same construction MLKEM768-X25519, and its HPKE KEM identifier is `0x647A`. `XWing` implements `Kem`. `XWingEncapsulationKey`, `XWingDecapsulationKey` (the 32-byte seed), `XWingCiphertext`, and `XWingSharedSecret` use the draft's raw encodings, which are also the HPKE serializations. `XWingEncapsulationKey::prepare` validates the ML-KEM-768 part one time for repeated encapsulation, and `XWingDecapsulationKey::prepare` (or `prepare_in` with `alloc`) expands the key one time for repeated decapsulation. The expanded keys have no encoding, because the draft forbids their transfer. The one difference from the -11 text: encapsulation and decapsulation reject an all-zero X25519 shared secret with `XWingError::InvalidEncapsulationKey` or `XWingError::InvalidCiphertext`, as X-Wing pull request 39 and RFC 9180 specify. X25519 clamps its scalar, so that result depends only on the public key or ciphertext. X-Wing needs neither allocation nor operating-system entropy, and builds on rscrypto's ML-KEM-768, X25519, SHAKE256, and SHA3-256.
